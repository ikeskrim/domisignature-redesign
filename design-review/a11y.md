# Accessibility — WCAG 2.1 AA

Automated pass: `npm run audit:a11y` (axe-core via Playwright, WCAG 2.1 A + AA),
10 routes × 2 viewports, against the **production build**. Raw output in
`a11y-axe.json`.

---

## Findings and fixes

### 1. Colour contrast — 20 violations → fixed

The three muted text tokens failed AA against the two page surfaces. They were
re-derived and are now quoted against `chalk` (#ebe8e1), the darker surface, so
both surfaces pass:

| Token | Was | Now | Contrast on chalk | Used for |
|---|---|---|---|---|
| `drift` | `#c9c3b6` | `#8a8375` | 3.03:1 | oversized chapter numerals (large text, 3:1 bar) |
| `stone` | `#a5a096` | `#6b665c` | 4.66:1 | small uppercase meta, eyebrow labels |
| `clay` | `#736e63` | `#5e5950` | 5.65:1 | muted body copy |

This is a visible change — the muted greys are darker than the Phase 4 design.
It was required to clear AA.

### 2. Low-opacity text on the dark scenes — fixed

`text-limestone/40` over `ink` measured **3.58:1**, and over `charcoal`
(the CTA block) **3.58:1** — both under the 4.5:1 bar for small text. Every
text use of limestone at 40/45/50% opacity was raised to 55/60%, which measures
**5.74:1 on ink** and **5.50:1 on charcoal**. Borders and backgrounds at low
alpha were left alone — they carry no text.

### 3. `<ol>` containing non-`<li>` children — fixed

Homepage journey teaser: the hairline rule and the "Read the full guide" button
sat as direct children of the `<ol>`. Both moved outside the list.

### 4. `<dl>` / `<dt>` / `<dd>` nesting — fixed

The contact page wrapped each `dt`/`dd` pair in *two* nested divs (a
`motion.div` from `Reveal`, then a styling div). `Reveal` now renders that div
itself, so each pair sits in a single `<div>` directly inside the `<dl>`.

### 5. Label type below the brief's 11px floor — fixed

The layout audit (`scripts/layout-audit.mjs`) found uppercase label type
rendering at 9.6–10.9px. Every value below `0.6875rem` (11px) was raised to it.

## Recorded exemption — footer wordmark (approved, Phase 6)

**Status: closed. axe now reports 0 violations across all 10 routes at both
viewports.**

The oversized `DOMISIGNATURE` clipped by the bottom edge of the footer is
`text-bone/12` on ink — roughly **1.2:1**, well under the 4.5:1 bar.

It is claimed under the **WCAG 1.4.3 exemption for text that is part of a
logotype or is purely decorative**. The grounds:

- It carries no information. The brand name is already present in the header
  wordmark, the footer contact column, the `<title>` and the page's structured
  data — a visitor loses nothing if they never perceive it.
- It is hidden from assistive technology: `aria-hidden="true"` on both the
  container and the span, so it is never announced.
- It is presentation, in the same sense a background image is.

Implementation: the span carries `data-a11y-exempt="decorative-logotype"`, and
`scripts/a11y.mjs` excludes that selector explicitly rather than the run simply
ignoring the failure. The exemption is therefore visible in the code, in the
audit script and here.

Approved by the client, Phase 6. Raising the opacity to ~`/45` would clear it
mechanically but would turn a watermark into a loud graphic, which was rejected.

## Superseded — the finding this replaced

**One violation, on every page:** the giant `DOMISIGNATURE` watermark clipped by
the bottom edge of the footer. It is `text-limestone/12` on ink — roughly
**1.2:1**.

It is deliberately a whisper, it sits inside an `aria-hidden` container, and it
duplicates the brand name already present in the header, the footer contact
column and the page title. By intent it is decoration, not content.

To clear axe it would need to go to roughly `limestone/45`, which would turn a
watermark into a loud graphic and change the footer's character.

**Options — your call:**

1. **Leave it** and record a documented WCAG 1.4.3 decorative-text exception. (My recommendation.)
2. Raise it to `/45` and accept the louder footer.
3. Replace the text with an inline SVG of the wordmark, which removes it from
   the contrast rule's scope entirely while looking identical.

Nothing has been changed here pending your answer.

## Manual review

Verified by code inspection and by driving the production build:

| Area | State |
|---|---|
| Skip link | Present, first focusable, targets `#main` |
| Landmarks | `header` / `main` / `footer` / `nav[aria-label]` on primary, mobile, footer and breadcrumb navs |
| Venues index — focus parity with hover | `onFocus` raises the image, `onBlur` clears it, siblings dim identically |
| Lightbox | `role="dialog"`, `aria-modal`, Escape closes, ←/→ navigate with wrap, focus moves in on open and returns to the trigger on close, background scroll locked |
| Mobile menu | `aria-expanded` + `aria-controls`, Escape closes, body scroll locked, closes on route change |
| Accordion | Button + `aria-expanded` + `aria-controls`, panel `role="region"` + `aria-labelledby` |
| Filters (events) | `aria-pressed`, plus an `aria-live` count so filtering is announced |
| Focus visibility | Single global `:focus-visible` — 2px `lamp` outline with 3px offset, applied over imagery and dark scenes alike |
| Alt text | Sourced from the content files; `alt=""` only on decorative and scrim imagery. The hero poster, venue covers, journey steps and team portraits all carry descriptive alt |
| Heading order | One `h1` per page; the venue title card supplies it, so no `h1` is duplicated by the page header |
| Reduced motion | Honoured globally in CSS **and** per-component via `useReducedMotion`; Lenis and the hero film do not initialise at all, and the axe sweep runs with reduced motion emulated to confirm content is reachable in that state |
| Form | The Monday.com form is a third-party document we cannot relabel; the direct phone / WhatsApp / email column sits alongside it at every breakpoint, and a fallback with those three appears if the iframe fails |

### Lighthouse accessibility category

95–96 on every page, both presets. See `lighthouse.md`.

## Not verified here

- **No real screen-reader pass** (NVDA / VoiceOver). axe and manual inspection
  do not substitute for one.
- **No real-device keyboard pass.** Focus behaviour was verified from the code
  and the DOM, not by physically tabbing a browser.
- **Firefox could not be launched** in this environment (`spawn UNKNOWN`), so no
  engine-specific focus or contrast check there.
